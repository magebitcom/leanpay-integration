# Release Notes - Category Page Performance, Installment Widget Fixes

**Date:** October 1, 2026
**Version:** 0.17.0
**Type:** Bug Fix / Performance / Feature
**Ticket:** LMM-146, LMM-150

---

## Overview

This release removes three database query patterns that made the installment box expensive to render on product listings. Time spent in the module's own queries on a category page is reduced by roughly 98%, and the queries no longer scale with the number of products shown.

Reported by Creatim (Andrej Parovel) via Leanpay, after OBI disabled the divided price box on category pages for performance reasons.

The release also includes LMM-150: an empty Minimum or Maximum Order Total no longer hides the installment widget, several settings are now read per store view instead of only at default scope, and a new admin setting chooses the Hyvä widget design. See [Installment Widget Fixes and Design Setting (LMM-150)](#installment-widget-fixes-and-design-setting-lmm-150).

---

## Problem Statement

### 1. One category lookup per product card (the reported issue)

On category, search and widget listings the module resolved the category promotion separately for every product card. Each card ran its own `catalog_category_product` lookup, with the product ID as a single-element `IN` list, plus a fresh category collection load, with no memoisation:

```sql
select category_id from catalog_category_product where product_id in (706) group by category_id
```

The query count scaled exactly with the number of cards: 12 products meant 12 lookups, 36 meant 36.

### 2. A full table scan per product card

`Helper\InstallmentHelper::canShowInstallment()` calls `getInstallmentCurrencies()`, which runs `SELECT DISTINCT currency_code FROM leanpay_installment`, once for every rendered price box and with no memoisation. `currency_code` was covered only by a fulltext index, which MySQL cannot use for this query, so every call scanned the entire table. On a table of 263,953 rows each call took a steady 54 ms.

This, not the reported category lookup, was the dominant cost. On a 36 card page it accounted for 1.94 seconds of a 3.80 second response.

### 3. Unindexed installment lookups

`getLowestInstallment()`, `getToolTipData()` and `getInstallmentList()` all filter on `loan_amount` and `group_name`. Neither column was indexed. The table's only btree index covered `installment_amount` and `installment_period`, which are the columns these queries read rather than the ones they search, so they scanned the table as well, at roughly 32 ms each.

---

## What's Fixed

### Batched category promotion loading

`Helper\Data` now keeps a per-request map of product to category IDs and of category ID to loaded category, filled by a new public `preloadCategoryPromotions()` method using one batched query pair. The listing block plugins call it once from the already loaded product collection, covering the standard theme category grid, search results and product widgets. The Hyvä integration calls it from its own listing hook.

Call paths outside a listing (product page, cart, checkout) fall through to the same batched load for their own items, so behaviour there is unchanged.

The raw string-built SQL has been replaced with a select using a bound `IN` list.

### Cached currency lookup

`Model\ResourceModel\Installment::getInstallmentCurrencies()` resolves once per request instead of once per rendered box.

### New index

A btree index on `loan_amount`, `group_name` and `api_type` has been added to `leanpay_installment`, matching the columns the installment lookups actually filter by.

## Measured Impact

Measured on a staging environment against the same category page, with a full cache flush before every request, on a `leanpay_installment` table of 263,953 rows.

| Products shown | Response before | Response after | Module DB time before | Module DB time after |
|---|---|---|---|---|
| 12 | 1.62 s | 0.67 s | 1.08 s | 0.07 s |
| 24 | 2.75 s | 0.81 s | - | 0.06 s |
| 36 | 3.81 s | 0.99 s | 2.85 s | 0.06 s |

| Query pattern | Before (36 cards) | After (36 cards) |
|---|---|---|
| Category promotion lookups | 36 | 1 |
| `DISTINCT currency_code` scans | 36 | 1 |
| Other installment lookups | 907 ms | 6 ms |

The page is between 2.4 and 3.8 times faster depending on how many products are listed. The larger the listing, the larger the gain.

## What Is Not Addressed

The total query count on a category page still grows with the number of products, from roughly 486 at 12 cards to 1,105 at 36. That growth is Magento's own work for configurable products on a listing: tier prices, child product and stock lookups, media gallery and product attributes, around 27 queries per card. It is not module code and it affects any store showing configurable products on a listing. Those queries are individually fast, which is why the response time no longer tracks them closely.

The fulltext index on `group_id`, `group_name`, `currency_code` and `api_type` has been left in place. No module query uses `MATCH` or `AGAINST`, so it serves nothing and adds cost to the nightly import, but removing it is a separate schema change.

## Technical Details

### Affected Components

- `Helper/Data.php` - added `preloadCategoryPromotions()` and `loadPromotionCategories()`, a per-request cache and an attribute constant; `validateCategory()` now resolves from that cache
- `Plugin/Block/Product/ListProductPlugin.php` - preloads from the loaded listing collection
- `Plugin/Block/Product/ProductsListPlugin.php` - preloads from the widget's product collection
- `Model/ResourceModel/Installment.php` - `getInstallmentCurrencies()` is memoised per request
- `etc/db_schema.xml` - new btree index `LEANPAY_INSTALLMENT_LOAN_AMOUNT_GROUP_NAME_API_TYPE`; the existing btree index referenceId was also corrected to match the name already present in the whitelist and in deployed databases
- `etc/db_schema_whitelist.json` - registers the new index and the `api_type` column, which was missing

### Upgrade Notes

- The index is created automatically by `bin/magento setup:upgrade`. On a large `leanpay_installment` table expect the upgrade to take slightly longer than usual while the index builds.
- The LMM-146 changes require no configuration changes and add no admin settings. LMM-150 adds one setting and changes how existing settings are read, see its upgrade notes below.
- The Hyvä compatibility module requires version 0.17.0 or newer of this module to get the listing preload. Older payment module versions paired with a newer Hyvä module skip the preload rather than failing.

## Testing Recommendations (LMM-146)

1. Category page with 12 or more products in a category that has a Leanpay promotion configured: the box renders on every card with the same financing product as before
2. With a query log or profiler and a cold cache, confirm one category promotion lookup and one `DISTINCT currency_code` query per page, regardless of the products-per-page setting
3. Compare response time at 12, 24 and 36 products per page: the time should grow far more slowly than before
4. Product in two promoted categories: the same promotion wins as before (inclusive first, then priority)
5. Exclusive category promotion with a non-promoted product in the cart: default financial product, as before
6. Time-based category promotion with an end date of today is active, and of yesterday is not, confirming the LMM-143 date handling is intact
7. Product page and checkout redirect for a product with a category-only promotion: unchanged
8. Home page or CMS product widget: installment boxes render and are batched
9. The LMM-110 category page display toggle still shows and hides the boxes
10. Confirm `bin/magento setup:upgrade` creates the new index on `leanpay_installment`

## Installment Widget Fixes and Design Setting (LMM-150)

Reported via Leanpay for iHunt (SI), a Hyvä store where the installment widget did not appear on the product page after a fresh install.

### Problem Statement

#### 1. An empty Minimum or Maximum Order Total hid the widget

`payment/leanpay/min_order_total` and `payment/leanpay/max_order_total` have no default value, so both are empty on a fresh install. `Helper\InstallmentHelper::getLowestInstallmentPrice()` compared the price directly against the empty value, and in PHP `160 > null` is true. The price was treated as above the maximum and the widget was hidden for every product.

Magento's own payment method availability check treats an empty minimum or maximum as no limit, so the Leanpay payment method could be available at checkout while the installment widget was hidden.

#### 2. Some settings were only read at default scope

The following settings can be saved per website or store view in admin, but were read at default scope only, so a value saved at website or store view level was ignored:

- Show installment price in following pages (`payment/leanpay/installment_allowed_views`)
- More information URL (`payment/leanpay_installment/more_info`)
- Check your limit URL (`payment/leanpay_installment/check_your_limit`)
- Leanpay currency, in the check that hides the widget when no installment data exists for the store currency (`payment/leanpay/leanpay_currency`)

#### A note on `bin/magento config:show`

`config:show` does not display defaults from a module's `config.xml`, only values saved in the database, `env.php`, `config.php` or environment variables. An empty result for `payment/leanpay/installment_allowed_views` therefore does not mean the setting is missing: its default (`HOMEPAGE,PRODUCT_PAGE,CATEGORY_PAGE`) still applies at runtime.


### What's Fixed

#### Empty limits mean no limit

An empty Minimum or Maximum Order Total is now ignored instead of hiding the widget, matching Magento's payment method availability check. Prices outside the amounts Leanpay offers plans for still show no widget, because the installment lookup only returns a value for loan amounts present in the synced installment data.

#### Store-scoped config reads

The four settings above are now read for the current store view, so website and store view values take effect.


### What's New

#### Installment widget design setting (Hyvä only)

**Stores → Configuration → Sales → Payment Methods → Leanpay Installment price → Installment Widget Design**

| Option | Widget | Calculator |
|---|---|---|
| Default (default value) | Full widget | Opens as a dropdown directly below the widget |
| Narrow | Compact widget, built for narrow sidebar layouts | Opens as a centred modal on desktop, bottom sheet on mobile |

The setting is available at default, website and store view scope. It is used by the Hyvä compatibility module (`leanpay/payment-hyva` 0.2.0 or newer) and has no effect on Luma themes.


### Technical Details

#### Affected Components

- `Helper/InstallmentHelper.php` - store-scoped reads for allowed views, more info URL, check your limit URL and the currency check; empty min/max treated as no limit; new `getInstallmentDesign()` and `LEANPAY_INSTALLMENT_DESIGN` constant
- `Model/Config/Source/InstallmentDesign.php` - new source model with the Default and Narrow options
- `etc/adminhtml/system.xml` - new `payment/leanpay_installment/design` field
- `etc/config.xml` - `design` default value `default`

#### Upgrade Notes

- No database changes. Run `bin/magento cache:flush` after upgrading.
- Stores with an empty Maximum Order Total will start showing the widget for every product with installment data. Set a maximum if the widget should be limited.
- Stores that saved "Show installment price in following pages", the more info URL, the check your limit URL or the Leanpay currency at website or store view level will now see those values applied.
- Hyvä stores: see the `leanpay/payment-hyva` 0.2.0 release notes. The product page widget changes from Narrow to Default unless Narrow is selected in admin.


### Compatibility

- Backward compatible; no configuration changes required
- No changes to calculated amounts or tooltips
- Applies to all regions; not specific to any plugin locale


### Testing Recommendations

1. Clear Minimum and Maximum Order Total at default scope, flush cache: the widget shows on the product page
2. Minimum 100, Maximum 5000: a 160 € product shows the widget; products below 100 € or above 5000 € do not
3. Allowed views set to Product at default scope and to Category only at website scope: the product page no longer shows the widget
4. More information URL changed at website scope: the calculator link uses the new URL
5. Installment Widget Design is shown under Color Theme, set to Default, and can be changed per store view
6. Luma storefront: widget unchanged regardless of the design setting
